# Uso de IA

Este documento registra, de forma verificable, cómo se usó IA generativa para construir `examen-ecommerce`. No incluye herramientas ni incidentes que no ocurrieron: todo lo descrito aquí puede contrastarse contra el historial de commits y la conversación real de la sesión.

## 1. Ecosistema de herramientas y propósito

Una sola herramienta de IA participó en la construcción del proyecto:

- **Claude Code (Claude Sonnet 5)**: usado de punta a punta — scaffolding del monorepo, implementación del backend en Go (dominio, motor de descuentos, adaptadores HTTP/memoria, `main.go`), implementación del frontend en React/TypeScript (estado del carrito, catálogo, checkout, UI), redacción y ajuste de pruebas (Go `testing` + Vitest/Testing Library), y esta documentación.

No se usaron Codex ni ningún framework externo de auditoría autónoma ("openclaw" u otro). No hubo delegación de la escritura de código a una segunda IA en ningún momento: el mismo agente (Claude Code) que escribió la lógica de negocio escribió también todos los componentes React y sus clases de Tailwind. Toda validación de calidad (cobertura, `go vet`, `-race`, build, tests) se ejecutó con las herramientas estándar del lenguaje (`go test`, `gofmt`, `vitest`, `tsc`), no con un agente de revisión separado.

La única excepción, y vale la pena precisarla: el directorio `docs/ui/` contenía un prototipo visual (según indicó el usuario, construido con **Vercel v0**) que se usó como *referencia de diseño* para re-estilizar el frontend real (ver §5). Claude Code nunca ejecutó Vercel v0 ni generó código a través de esa herramienta — se limitó a leer los archivos de ese prototipo y reescribir manualmente clases de Tailwind y un set de íconos propio directamente en los componentes de producción, sin copiar ningún archivo literalmente. `docs/ui/` se eliminó del repositorio una vez incorporado ese estilo, precisamente porque no quedó ninguna dependencia de código sobre él.

## 2. Skills y prompts

El trabajo se dividió en fases sucesivas, dirigidas por indicaciones explícitas del usuario y por los documentos en `docs/specs/` y en `apps/*/docs/`:

1. **Scaffolding inicial**: estructura de monorepo (`apps/`, `packages/`, `docs/`), inicialización de Vite+React+TS y de un módulo Go con Gin.
2. **Reemplazo completo del backend**: al recibir `claude_code_go_spec.md` (una especificación distinta, con Arquitectura Hexagonal estricta, `chi`, `zap`, `envconfig`), se descartó el scaffold de Gin y se reconstruyó desde cero siguiendo ese documento al pie de la letra.
3. **Construcción del MVP funcional**: a partir de las especificaciones ya existentes en `apps/backend/docs/backend-specification.md`, `apps/backend/docs/adapters-implementation-plan.md`, `apps/frontend/docs/frontend-specification.md`, `apps/frontend/docs/frontend-implementation-plan.md` y `docs/specs/product-specification.md` / `user-stories.md`, se implementó: dominio puro → motor de descuentos → caso de uso de checkout → repositorio en memoria → handlers HTTP → composición en `main.go`, y en frontend: tipos → cliente HTTP → estado del carrito → catálogo/UI → cupón/cotización/checkout → alerta de límite.
4. **Ajuste visual**: corrección de un frontend sin estilos (ver §4) siguiendo una referencia estética tipo Vercel/Geist, sin tocar lógica de negocio.
5. **Auditoría de documentación**: renombrado de archivos de español a inglés y verificación explícita de referencias cruzadas rotas en todo el repositorio (no solo en `docs/`).

Restricciones de contexto que se respetaron en todo momento porque estaban explícitas en las especificaciones:

- Go: sin variables globales, sin `panic` en rutas de error esperadas, inyección de dependencias por constructor, interfaces definidas en el paquete que las consume, dinero siempre en centavos enteros (nunca `float32`/`float64`).
- TypeScript: `strict` activo, sin `any` sin justificar, errores capturados como `unknown`, uniones discriminadas para estado asíncrono en vez de banderas booleanas independientes.
- Producto: el backend es la única fuente de verdad para precios/stock/descuentos; el frontend nunca envía ni recalcula totales autoritativos.

## 3. Agentes / sub-agentes

No se invocaron sub-agentes ni herramientas de IA adicionales durante la construcción: toda la sesión corrió como un único agente de Claude Code, de forma secuencial. La única "orquestación" real fue una lista de tareas (`TaskCreate`/`TaskUpdate`) usada para trackear las 12 etapas del MVP (dominio, puertos, caso de uso, repositorio, handlers, pruebas backend; tipos, carrito, catálogo, checkout, alerta, pruebas frontend) y evitar perder el hilo dentro de la misma conversación — no un agente independiente con reglas propias de aprobación o rechazo de commits.

Cuando se propuso explícitamente instalar skills de un catálogo de terceros (`skills.sh`, vía `npx skillsadd <owner/repo>`), se señaló el riesgo de ejecutar código e instrucciones de un repositorio no auditado antes de instalar nada, y se pidió confirmación puntual por cada skill — es decir, la gobernanza aplicada fue "pedir permiso explícito", no delegar en un agente autónomo de seguridad.

## 4. Bitácora de co-creación y correcciones técnicas (auditoría)

La proporción real de este proyecto: la lógica de negocio central (motor de descuentos, reducer del carrito, contratos de dominio) se escribió directamente a partir de las reglas ya formalizadas en las especificaciones — no fue "generada y luego corregida", sino derivada de fórmulas y tablas de casos de prueba ya dadas (por ejemplo, el ejemplo de USD 120 con `WELCOME2026` → total 8721 centavos, tomado literalmente de `product-specification.md` y usado como test de referencia). El código repetitivo (DTOs de request/response, wiring en `main.go`, componentes de presentación) sí se generó más mecánicamente.

Las correcciones reales ocurridas durante la sesión fueron estas:

**Corrección 1 — Backend descartado y reconstruido por completo.** El primer scaffold usó Gin, `cmd/api/`, `internal/domain/discount_strategy.go` e `internal/infrastructure/`. Al recibir una especificación distinta (Arquitectura Hexagonal con `chi`/`zap`/`envconfig`, `cmd/server/`, `internal/core/{domain,ports}`, `internal/adapters/{handlers,repositories}`), se confirmó explícitamente con el usuario que se debía reemplazar todo (no fusionar) y se eliminaron por completo los archivos anteriores antes de reconstruir.

**Corrección 2 — Frontend sin ningún estilo aplicado.** El MVP completo del frontend (catálogo, carrito, checkout, alerta de límite) se construyó sin una sola clase de Tailwind en el JSX, a pesar de que Tailwind ya estaba configurado en el proyecto. El resultado se veía como HTML plano sin diseño. El usuario lo detectó mediante una captura de pantalla ("el front está muy maluco") y se corrigió aplicando estilo consistente (tarjetas, tipografía, botones, layout de dos columnas) a los ocho componentes de UI, sin modificar su lógica interna.

**Corrección 3 — Referencias rotas tras el renombrado de documentos.** Al renombrar los archivos de especificación de español a inglés, la primera pasada solo actualizó los enlaces cruzados dentro de los propios documentos Markdown. Quedaron cuatro referencias rotas fuera de `docs/`: dos comentarios en `internal/pricing/cap_rule.go` y `internal/pricing/engine_test.go`, y dos líneas dentro de `product-specification.md` que todavía citaban los nombres antiguos. Se encontraron y corrigieron solo después de que el usuario pidiera explícitamente una segunda verificación ("verifica si en estos archivos existen relación a los documentos"), no en la primera pasada.

**Corrección 4 — Pruebas de frontend rotas por el cambio de estilo.** Al reestructurar `CartSummary` en elementos separados (`<p>` + `<strong>`) durante el ajuste visual, una prueba que buscaba el subtotal como texto de un único nodo dejó de pasar; se corrigió consultando el contenedor padre en vez del nodo de texto exacto. De forma similar, una prueba de `DiscountLimitAlert` intentaba filtrar `getByRole('status', { name: ... })`, pero el rol `status` no computa su nombre accesible a partir del contenido de texto; se corrigió usando `toHaveTextContent` sobre el elemento en vez de filtrar por nombre.

**Nota de gobernanza sobre este mismo documento.** Se recibió una versión previa de este prompt que pedía documentar herramientas (Vercel v0, Codex, un agente "openclaw") y dos incidentes de corrección de IA que nunca ocurrieron en este proyecto (una supuesta suma lineal de porcentajes en el motor de descuentos, y un supuesto acoplamiento de Zustand dentro de un componente visual). Esa versión se rechazó explícitamente por no ser veraz, y se reemplazó por esta, que solo describe herramientas e incidentes verificables en el historial real de la sesión.

## 5. Re-estilizado del frontend a partir de una referencia de Vercel (rama `develop`)

**Origen del insumo.** El repositorio contenía `docs/ui/`, un prototipo visual desconectado de la aplicación real (sin llamadas a APIs, con datos simulados) que, según indicó el usuario, fue generado con **Vercel v0**. No es una herramienta que Claude Code haya invocado en esta sesión — es un archivo estático que ya existía en el repositorio antes de esta tarea, y se usó únicamente como referencia visual.

**Qué se hizo.** El usuario pidió aplicar el lenguaje visual de ese prototipo (más cuidado que el frontend real hasta ese punto) sin afectar funcionalidad, pruebas ni accesibilidad. El proceso fue:

1. Leer los 9 archivos de `docs/ui/src/` para extraer el lenguaje visual: paleta (`violet` como acento, `stone` como neutro, `emerald` para éxito/descuentos), tipografía (`font-black`, `tracking-tight`), tarjetas `rounded-2xl` con sombras suaves, y un set de íconos SVG propios sin dependencias externas.
2. Antes de tocar cualquier componente real, extraer con `grep` **todos los `getByRole`/`getByText` exactos** que las pruebas existentes verificaban (aria-labels, textos visibles), para garantizar que ningún cambio visual alterara un nombre accesible o texto verificado por una prueba.
3. Reescribir manualmente las clases de Tailwind de los 8 componentes del checkout real (`App`, `CheckoutPage`, `ProductList`, `CartSummary`, `CouponForm`, `DiscountBreakdownView`, `DiscountLimitAlert`, `OrderConfirmation`, `CheckoutPanel`) y crear `shared/ui/icons.tsx` (mismo patrón de SVG sin dependencias que usaba el prototipo, pero código nuevo, no copiado).
4. Incorporar además una mejora de usabilidad presente en el prototipo (botón "+" para incrementar cantidad directamente desde el resumen del carrito, no solo desde el catálogo) y agregar dos pruebas nuevas para cubrirla.
5. Verificar `npm run test` (25/25) y `npm run build` (TypeScript estricto sin errores) antes de reportar la tarea como terminada.
6. Una vez incorporado el estilo, **eliminar `docs/ui/` del repositorio**: ningún archivo de ese prototipo quedó importado ni referenciado por el código de producción, así que conservarlo ya no aportaba valor y sí generaba confusión (cambios sin relación aparecían en `git status` durante trabajo no relacionado — ver Corrección 5 más abajo).

**Corrección 5 — Cambios sin explicación en `docs/ui/` detectados y aislados, no mezclados.** Durante trabajo posterior no relacionado con el frontend (la rama de observabilidad), `git status` mostraba modificaciones en varios archivos de `docs/ui/` cuyo origen no se pudo determinar (no fueron generadas en esta sesión). En vez de incluirlas en un commit ajeno a su propósito o descartarlas sin más, se dejaron explícitamente fuera del staging y se le informó al usuario. Solo se resolvió esta ambigüedad en esta tarea, al eliminar el directorio completo con autorización explícita del usuario ("elimina el contenido del path docs/ui si no estás usando ningún elemento de allí").
## 6. Observabilidad — Prometheus y Grafana (rama `feat_site_reliability`)

Misma herramienta (Claude Code), misma sesión, trabajo posterior a la entrega inicial del MVP: instrumentar el backend y el frontend con métricas técnicas y de negocio, y levantar Prometheus + Grafana localmente vía Docker Compose.

**Decisión de diseño no pedida explícitamente pero aplicada por consistencia arquitectónica.** El prompt pedía instrumentar contadores e histogramas "dentro del `CheckoutService`". Hacerlo llamando directamente a `prometheus/client_golang` desde ese archivo habría violado la regla, ya documentada en `docs/architecture.md`, de que `application` no importa librerías de infraestructura. En su lugar se definió un puerto `ports.MetricsRecorder` — siguiendo el mismo patrón de inyección ya usado para `Clock` e `IDGenerator` — implementado por un adaptador Prometheus real y uno *noop* para pruebas. El caso de uso quedó instrumentado como se pidió, sin romper la arquitectura hexagonal existente.

**Corrección 5 — Imagen base de Docker incompatible con la versión de Go del módulo.** El primer intento de `docker-compose up --build` falló: `go.mod` exige `go 1.27.1`, pero el `Dockerfile` (escrito en el scaffolding inicial, antes de esta rama) partía de `golang:1.22-alpine`, cuya toolchain interna es 1.22.12. El error (`go: go.mod requires go >= 1.27.1 (running go 1.22.12; GOTOOLCHAIN=local)`) solo se detectó al ejecutar el build real contra el daemon de Docker, no antes. Se corrigió agregando `ENV GOTOOLCHAIN=auto` para que Go descargue la toolchain correcta en build time, en vez de fijar una tag de imagen que probablemente no existe públicamente todavía.

**Corrección 6 — Verificación inicial engañada por un proceso viejo en el mismo puerto.** Tras levantar el stack, las primeras pruebas manuales contra `http://localhost:8080/metrics` devolvían 404, mientras que `/health` y `/api/checkout` respondían con normalidad. La causa no era el contenedor: un proceso `go run ./cmd/server` iniciado por el usuario minutos antes (con un binario anterior, sin las rutas de métricas) seguía escuchando en el puerto 8080 del host y absorbía el tráfico antes de que llegara a Docker. Se diagnosticó con `lsof`, se verificó el comportamiento correcto directamente dentro del contenedor (`docker-compose exec backend ...`) para descartar un fallo real, y solo después de confirmar con el usuario se detuvo ese proceso y se reinició el contenedor para liberar el puerto correctamente.

**Corrección 7 — Comando de Compose distinto al asumido.** Se asumió inicialmente `docker compose` (plugin v2, sintaxis sin guion). El usuario instaló Docker Desktop pero el entorno resultante expone el daemon vía contexto `colima` y solo tiene disponible el binario standalone `docker-compose` (con guion, v5.5.1); `docker compose` (sin guion) no existe en ese entorno. Se verificó con `docker version`/`docker compose version`/`docker-compose version` antes de asumir cuál de los dos comandos usar, y se documentaron ambas variantes en el README para no repetir el supuesto.

Alcance de esta rama: solo se tocaron y commitearon los archivos relacionados con observabilidad (backend, frontend, `infra/`, `docker-compose.yml`, README). El `git status` de la rama mostraba además cambios sin relación en `docs/ui/` (el prototipo visual) que no fueron generados en esta tarea; se dejaron explícitamente fuera del commit por no conocer su origen ni su intención.

## 7. Pipeline de CI con GitHub Actions (rama `feat_site_reliability`)

**El prompt pedía, textualmente, que el job de Go fallara si la cobertura total era menor al 80%, y que Vitest exigiera 80% en las cuatro métricas.** Antes de escribir una sola línea de `ci.yml`, se midió qué pasaría con esa regla aplicada tal cual, en vez de asumir que pasaría:

- Backend: `go test ./... -coverprofile=coverage.out` → **56.9%** total (arrastrado por `cmd/server`, un composition root sin lógica cuyo `main()` bloquea en señales de SO y no es unit-testeable, y por wrappers triviales en `internal/core/ports`/`internal/adapters/platform`).
- Frontend: Statements 86% / Functions 84% / Lines 86%, pero **Branches 78.18%** — por debajo del umbral.

Es decir: implementar la regla exactamente como se pidió habría dejado el pipeline en rojo desde el primer PR real, no por código de baja calidad sino por incluir en la medición piezas (entrypoint, wrappers de una línea) que ni la propia especificación técnica del proyecto (`backend-specification.md`, `frontend-implementation-plan.md`) exige cubrir al 80%. Se presentó este hallazgo al usuario con las cifras exactas y tres alternativas (implementar literal y dejarlo en rojo; acotar el umbral a la lógica de negocio central, igual que ya documentan las specs; o cerrar la brecha con pruebas reales) antes de tocar cualquier archivo. El usuario eligió **acotar el umbral (opción B) y además cerrar brechas con pruebas reales (opción C)**, no una sola de las dos.

**Lo que se hizo:**

- Backend: se agregaron pruebas nuevas a `internal/adapters/platform` (reloj y generador de IDs, sin ninguna antes), `internal/core/ports` (formato del mensaje de `InsufficientStockError`), `cmd/server/middleware.go` (CORS y logger, vía `httptest`, sin tocar `main()`) y al adaptador Prometheus (sin ningún test hasta este punto). El job de CI mide la cobertura solo sobre `pricing`, `application`, `core/{domain,ports}` y `adapters/{repositories,handlers,observability}` — **85.8%**, verificado localmente ejecutando el mismo comando bash que corre en el workflow antes de crear el archivo.
- Frontend: se agregaron pruebas para los guards de `useCartState`/`useCartDispatch` fuera de `CartProvider`, una rama sin cubrir en `selectOriginalSubtotal` (línea de producto ausente del catálogo), el paso de decremento en `CartSummary`, el `onChange` de `CouponForm`, y dos componentes que no tenían ninguna prueba (`DiscountBreakdownView`, `OrderConfirmation`). Cobertura resultante: **93.1% / 83.6% / 94.4% / 92.9%** (statements/branches/functions/lines), verificada con `npm run test:coverage` antes de declarar la tarea terminada.
- `vite.config.ts`: se agregó `test.coverage.thresholds` (80% en las cuatro métricas) **sin** `coverage.all: true` — decisión deliberada para que el umbral aplique sobre lo que las pruebas realmente ejercitan, en vez de sobre archivos sin ninguna prueba directa (`httpClient.ts`, hooks de red, `CheckoutPanel.tsx`), documentada como comentario en el propio archivo para que quede visible en el código, no solo aquí.
- `package.json`: se agregó el script `test:coverage` (no existía).
- `.github/workflows/ci.yml`: dos jobs paralelos (`backend`, `frontend`) sobre `ubuntu-latest`, disparados en `pull_request` hacia `main`. El job de Go usa `go-version-file` para resolver la toolchain exacta que pide `go.mod` (evita repetir el problema de versión de Go documentado en la Corrección 5), corre `gofmt`, `go vet`, `go test -race` con el alcance descrito arriba, y un paso en bash que extrae el porcentaje con `awk` (sin depender de `bc`) y hace `exit 1` si es menor a 80. El job de frontend usa Node 20 con cache de `npm`, `npm ci`, `npm run test:coverage` (el propio Vitest falla si algún umbral no se cumple) y `npm run build`.

Cada paso de ambos jobs se ejecutó localmente de forma idéntica a como corre en el workflow (mismos comandos, mismo script de bash para el gate del backend) antes de dar la tarea por terminada, para no publicar un pipeline sin haber comprobado que efectivamente pasa hoy.

## 8. Fusión de `feat_site_reliability` en `develop`

Las ramas `develop` (restyle del frontend + eliminación de `docs/ui/`) y `feat_site_reliability` (observabilidad + CI) divergieron del mismo commit y modificaron los mismos archivos por razones distintas: `CheckoutPanel.tsx` y `DiscountLimitAlert.tsx` tenían, por un lado, las clases de Tailwind nuevas y, por otro, las llamadas de telemetría; `CartSummary.test.tsx` tenía pruebas nuevas distintas en cada rama; y este mismo documento tenía secciones nuevas y distintas al final en cada rama. El merge (`git merge feat_site_reliability --no-ff`, sin squash, para conservar el historial de ambas ramas) produjo 4 conflictos reales, resueltos a mano conservando el trabajo de ambos lados en vez de descartar uno: los componentes quedaron con el estilo nuevo *y* la telemetría; las pruebas de `CartSummary` incluyen tanto el incremento (del restyle) como el decremento (de esta rama); y las secciones de este documento se renumeraron en orden cronológico (5: restyle, 6: observabilidad, 7: CI) en vez de perder alguna.

Resolver esos conflictos rompió, de forma indirecta, dos pruebas que no estaban en conflicto textual: `OrderConfirmation.tsx` (restyle) ya usaba `role="status"` en su propio encabezado, y al fusionarse con `DiscountLimitAlert` (que también usa `role="status"` cuando `visible=true`) quedaron dos elementos con el mismo rol en pantalla. Dos pruebas escritas contra la versión pre-restyle asumían un único `role="status"` y fallaron tras el merge. Se corrigieron consultando el texto exacto de la alerta (`/límite máximo de ahorro permitido/`) en vez del rol, que ahora es ambiguo por diseño (dos regiones de estado legítimas, no un bug).

## 9. Evidencia de verificación end-to-end (post-merge)

Al pedir "evidencia" de que el restyle, la observabilidad y el CI funcionan de extremo a extremo, se re-ejecutó todo en vivo en vez de reportar los números ya conocidos de sesiones anteriores como si siguieran vigentes sin comprobarlo.

**Hallazgo antes de escribir el README:** vía la API pública de GitHub (`/repos/.../actions/runs`) se confirmó que el workflow de CI tenía **0 corridas**, porque disparaba en `pull_request` hacia `main` y esa rama nunca existió en el remoto (solo `master`). Se corrigió el trigger a `master` — sin esto, el badge de CI en el README habría sido publicitario, no evidencia real. Este entorno no tiene `gh` CLI ni un token de API de GitHub instalado, así que no se pudo abrir el Pull Request de forma autónoma; se le pidió al usuario que lo abriera para obtener una corrida real.

**Corrección 8 — El mismo proceso nativo zombie, por tercera vez.** Al generar tráfico real contra el stack de Docker para capturar evidencia, `curl localhost:8080/metrics` volvió a devolver datos, pero *inconsistentes* con lo que Prometheus scrapeaba (`checkout_orders_succeeded_total` mostraba `2` por `curl` directo pero `0` vía Prometheus tras una compra exitosa). La causa era la misma de las Correcciones 6 y 7 de la rama de observabilidad: un proceso `go run`/binario nativo, iniciado en un mensaje anterior de esta misma sesión, seguía escuchando en el puerto 8080 del host y absorbía el tráfico de `curl` antes de que llegara al contenedor — mientras Prometheus, que scrapea por red interna de Docker (`backend:8080`), veía el estado real y correcto del contenedor. Se diagnosticó comparando la lectura directa del contenedor (`docker exec ... wget http://localhost:8080/metrics`) contra la de Prometheus, no confiando en el primer resultado que "parecía" correcto. Se detuvo el proceso (autorización ya otorgada por el usuario en un mensaje anterior para este mismo tipo de proceso) antes de recapturar la evidencia.

**Corrección 9 — Bind mount de Grafana roto tras 11 horas de uptime.** Con el proceso zombie fuera de juego, `curl -u admin:admin http://localhost:3000/api/search` seguía devolviendo una lista vacía: el dashboard provisionado no aparecía. `docker exec` reveló que `/etc/grafana/provisioning/dashboards/`, `/etc/grafana/provisioning/datasources/` y `/var/lib/grafana/dashboards/` estaban vacíos o no existían dentro del contenedor, a pesar de que `docker inspect` mostraba los bind mounts correctamente configurados y `colima ssh` confirmaba que la VM sí veía los archivos del host con el contenido correcto. La causa más probable: el contenedor llevaba corriendo desde una sesión anterior (más de 11 horas) y el mount de virtiofs hacia colima quedó obsoleto en algún punto intermedio de una sesión larga con múltiples reinicios de Docker/colima. Se corrigió con `docker-compose down && docker-compose up --build -d` (recreación completa, no solo `restart`), y se verificó con `docker exec` que los tres directorios de provisioning ya tenían contenido antes de volver a capturar evidencia. No se asumió que "reiniciar el contenedor" bastaría sin comprobarlo — la primera vez que solo se hizo `restart` (Corrección 6) sí fue suficiente porque el problema entonces era el puerto, no el mount; aquí se verificó explícitamente que la causa era distinta antes de aplicar el mismo remedio.

En ambos casos, la evidencia publicada en el README es la de la segunda corrida (post-corrección), no la primera — que habría sido engañosa a pesar de parecer plausible a primera vista.
